# FPGA 项目提示词工作流

## 目的

本技能包把本项目中反复使用、可以迁移到其他 FPGA/AI 加速项目的分析过程整理成提示词模板。每次使用都必须同时提供代码或报告原文；模型只能根据提供的证据作出判断，不能把推测写成已验证结论。

本技能包包含两项工作流：

1. 从算法和接口描述推导软硬件划分。
2. 根据 Vivado 综合、实现和时序报告定位资源或时序瓶颈。

## 使用前的通用步骤

1. 准备任务描述、目标器件、时钟、输入输出接口和验收指标。
2. 收集与问题直接相关的源码、工程配置、约束文件和报告原文，并标注文件路径、工具版本和生成阶段。
3. 将材料填入下方对应模板，保留模板中的输出格式和“证据/推断/待验证”区分要求。
4. 让模型先给出分析表，再给出结论和验证计划；不要只要求模型直接改 RTL。
5. 按验证计划在 Vivado 仿真、综合、实现或板上测试中复核，并把实际结果记录到报告或指标表中。

---

## 工作流一：算法描述到软硬件划分

### 适用场景

算法已经有输入、输出、精度、吞吐量或延迟要求，需要决定哪些步骤放在 FPGA、哪些步骤放在 PS/上位机，以及接口和定点格式如何划分。

### 输入材料

- 算法步骤或伪代码。
- 输入数据位宽、采样率、帧长和有效信号定义。
- 目标器件、时钟和可用外设。
- 精度、吞吐量、延迟、功耗等约束。
- 已有 RTL、HLS、软件模块和实测数据（如有）。

### 提示词模板

```text
你是 FPGA 系统架构评审员。请根据下面的算法、接口和硬件约束，提出可复现的软硬件划分方案。

【目标】
{用一句话描述要完成的功能和验收指标}

【算法或伪代码】
{粘贴算法步骤；不要省略循环、窗口、归一化、量化和异常处理}

【输入输出】
{列出信号名、位宽、是否有符号、采样率/帧长、valid/ready 或触发关系}

【硬件约束】
器件：{part}
时钟：{clock}
可用资源：{LUT/FF/BRAM/DSP/IO；未知则写未知}
接口：{ADC、UART、AXI、DDR、GPIO 等}

【已有实现】
{粘贴相关 RTL/HLS/软件模块和工程配置；标明文件路径}

请严格按以下顺序输出：
1. 先列“已知事实”，每一项附文件路径或输入材料中的原文依据。
2. 给出候选划分表：步骤、建议位置（FPGA/PS/上位机）、原因、接口、位宽/定点格式、预计代价。
3. 画出从输入到输出的数据流（用纯文本箭头即可），标明时钟域和 valid/ready 边界。
4. 指出至少三项风险：溢出/符号、帧边界、时钟域、资源或带宽，并给出可执行的验证方法。
5. 给出“尚未证实的假设”清单。没有报告或实测证据的地方必须写“待验证”。
6. 给出最小验证顺序：仿真、综合、实现、板上测试分别检查什么，以及通过标准是什么。

不要凭空填写器件资源、时序或精度结果；不要在没有得到批准前改写代码。
```

### 本项目中的已验证参考

当前顶层 `project_1/project_1.srcs/sources_1/new/Correlation_Top.sv` 将 XADC 采样接入相关运算；相关结果通过 `meanOfData_nn` 和 `dataValid_nn` 送入 `Neural_network`。该实例明确设置 `NUM_OF_CHANNEL=90`、`OUT_FEATURES=3`、`BIT_WIDTH=8`、`RAW_DATA_W=24`。`Neural_network.sv` 中的链路是 24 位原始数据帧归一化为 8 位无符号值，再映射为有符号 8 位输入，随后进入三层全连接网络；`NN_module.sv` 的层宽由顶层覆盖为 90→50→30→3。

这些事实可用于检查模型是否正确解析了参数覆盖、符号转换和 valid 链路，但不能代替新的功能仿真或板上验证。

### 验证结果

使用上述材料进行人工复核时，模板能够把“XADC/相关运算/归一化/神经网络/UART”拆成独立阶段，并指出 24 位无符号原始值到 8 位有符号输入的转换点。验证时应至少检查：90 个特征是否完整输出、归一化帧边界是否与 `dataValid_nn` 对齐、`img_norm` 的 `-128~127` 范围是否正确，以及 NN 的 `done` 是否触发最终输出。

### 失效条件

- 只有自然语言算法，没有位宽、帧长或时序约束时，只能得到候选架构，不能声称划分已经验证。
- 代码中存在未提供的 IP、参数文件或软件协议时，接口结论必须标为待验证。
- 需要精确吞吐量、功耗或资源预测时，必须补充对应工具报告；模型估算不能替代 Vivado 结果。

## 工作流二：根据 Vivado 报告定位瓶颈

### 适用场景

综合或实现已经完成，需要从资源利用率、时序路径、功耗和 DRC/方法学警告中确定优先优化对象，并形成下一轮修改和复测计划。

### 输入材料

- `report_utilization` 的综合和实现报告。
- `report_timing_summary` 或关键路径报告。
- `report_methodology`、DRC 和功耗报告（如有）。
- 目标器件、时钟约束、综合/实现策略和本轮代码变更。

### 提示词模板

```text
你是 Vivado 实现结果分析员。请只依据我提供的报告，找出最值得优先处理的资源、时序或方法学问题。

【工程信息】
工程：{project}
工具版本：{tool_version}
器件：{part}
时钟约束：{clock_constraints}
本轮变更：{changes}

【综合资源报告】
{粘贴 report_utilization 相关表格，并标注文件路径}

【实现资源报告】
{粘贴 placed/routed utilization 表格，并标注文件路径}

【时序报告】
{粘贴 timing summary 和最差路径；包含 WNS/TNS/WHS/THS、周期、路径延迟和逻辑/布线延迟}

【方法学、DRC、功耗报告】
{粘贴相关摘要；没有则明确写“未提供”}

请严格按以下格式输出：
1. 资源表：资源、综合使用量/占比、实现使用量/占比、变化、证据路径。
2. 时序表：时钟、周期、WNS/TNS/WHS/THS、最差路径起点终点、逻辑延迟、布线延迟。
3. 按“必须修复/建议优化/暂不处理”分类列出问题，并解释分类依据。
4. 对每个必须修复或建议优化的问题，给出可能根因、最小改动方向和复测命令/报告。
5. 明确区分“报告直接证明”和“需要进一步验证的推断”。
6. 输出下一轮实验矩阵：一次只改变一个主要因素，记录资源、时序、功耗和功能回归结果。

不要把利用率最高自动等同于关键瓶颈；不要把 WARNING 自动等同于功能错误；不要修改 RTL 或约束文件。
```

### 本项目中的已验证参考

当前工程报告来自 Vivado 2024.2、器件 `xc7a100tfgg484-2`：

- 综合报告 `project_1/project_1.runs/synth_1/Correlation_Top_utilization_synth.rpt`：LUT 21018/63400（33.15%），寄存器 16696/126800（13.17%），DSP 84/240（35.00%），Block RAM Tile 1.5/135（1.11%）。
- 实现报告 `project_1/project_1.runs/impl_1/Correlation_Top_utilization_placed.rpt`：LUT 23030/63400（36.32%），寄存器 20662/126800（16.29%），DSP 174/240（72.50%），Block RAM Tile 1.5/135（1.11%）。
- 时序报告 `project_1/project_1.runs/impl_1/Correlation_Top_timing_summary_routed.rpt`：100 MHz 时钟 WNS 0.567 ns、TNS 0，WHS 0.033 ns、THS 0；最差路径的数据路径延迟为 6.233 ns，其中布线延迟 5.885 ns（94.417%）。
- 方法学报告 `project_1/project_1.runs/impl_1/Correlation_Top_methodology_drc_routed.rpt`：DPIR-1 有 4674 个 Warning，另有 SYNTH-4 2 个、SYNTH-6 3 个、XDCC-1 和 XDCC-7 各 1 个 Warning。

因此，模板在本项目上的示例结论是：先检查实现阶段 DSP 使用率显著升高的原因，再检查最差路径的高布线延迟和 DPIR-1 警告；当前报告同时显示时序约束已满足，不能把它写成“时序失败”。这只是报告诊断优先级，不是自动修改方案。

### 验证结果

模板可以从综合与实现报告中保留阶段差异，并把“DSP 72.50%”“WNS 0.567 ns”“布线延迟占 94.417%”“DPIR-1 4674”分别追溯到具体报告。复测时应重新生成同名报告，并确认工具版本、器件、约束和实现策略一致。

### 失效条件

- 只有综合报告而没有实现和时序报告时，不能判断布线瓶颈或最终时序。
- 报告来自不同器件、不同约束或不同提交版本时，不能直接比较数值。
- 报告中的 Warning 需要结合具体规则和路径分析；仅凭数量不能判断严重程度。
- 若报告已过期或设计状态不是当前源码生成的结果，必须先重新综合/实现，再使用该工作流。

## 提炼依据

本技能包来自本项目中的重复观察：顶层参数会覆盖子模块默认值，数据在多个时钟/valid 边界间传递，定点符号转换容易被忽略；同时综合和实现报告的资源数字不同，时序报告还需要把逻辑延迟与布线延迟分开阅读。上述风险和检查顺序因此被写入模板，并使用当前源码与报告完成了人工复核。
